# saos — simulate any optical system

Run commands from the saos repository root with `uv run saos …`. Every command prints one JSON object (`{"ok": true, "result": …}` or `{"ok": false, "error": {code, message, details}}`). Command help: `uv run saos --help` and `uv run saos <command> --help`. Demand format: [`skills/saos/demand.example.yaml`](demand.example.yaml), copy it and fill it in. Terms: `DESIGN.md` (English and Chinese names).

You are the designer. The workflow fixes only a few gates and invariants; how you model, which starting design you choose, which merit function, variables, optimiser and search strategy you use is your judgement. Think like an optical engineer: understand the physics of this particular system before you optimise it, and change your approach when the evidence says it is not working.

## Invariants (never break these)

1. **Record the need.** Keep the user's own words in `sources/interview.md` and the condensed, current need in `sources/demand.yaml`.
2. **Measured evidence.** Every number you deliver comes from an actual computation on the backend, Optiland or OpticStudio (operand, ray trace, analysis export, script), archived in the job with the backend that made it. Numbers measured in Optiland are reported as such: the final delivery takes OpticStudio numbers, which come after the user has accepted the Optiland result. Never report an estimate as a result.
3. **No silent relaxing.** If a goal cannot be met, say by how much. Changing a constant, a variable range or an objective requires going back to the user and a new confirmation.
4. **Real materials in what you deliver.** A delivered lens uses only materials with a source (catalog, library, datasheet, paper). A model glass (`nd`/`Vd` only) is fine for exploration; the tools mark such rounds as not deliverable.
5. **Reports are HTML.** Every report for the user (model review, design analysis, exploration results, verification, assembly plan, final delivery), whether a tool or you write it, is an `.html` file, and links between reports point to HTML. Skill files, the demand YAML, the interview record, internal working notes and raw measurement JSON keep the formats the workflow sets.

## Gates (where you always wait for the user)

1. **The need**: the user approves the demand; `saos demand confirm` records their words, bound to that version.
2. **The model**: the user approves the model description; `saos lens approve` records their words. `saos round` refuses a lens whose structure matches no approved description: the surface types, the class of medium (air, glass, mirror), aperture types, the stop, whether a Fresnel substrate is flat or a surface is tilted, and the system settings (fields and wavelengths may gain points at the end). The conditions of the checks are part of the model too: the number of configurations, each multi-configuration row's operand and parameters, TEMP and PRES values, environment temperature and pressure, apodization, polarization, the coating file and the afocal units; changing them changes the problem. Radii, thicknesses, conics, polynomial terms, tilt angles, aperture sizes, the other multi-configuration values (zoom spacings and the like), the choice of glass and the coatings of surfaces this design makes stay yours; glasses and coatings are recorded with every round. Surfaces you declare as environment (sample, media, bought-in parts) are locked further: material, coating, radius, conic, apertures and tilts.

3. **The Optiland result**: show the current report and wait for the user to accept it. `saos zos begin --job J --quote "<their words>"` seals that acceptance and starts the OpticStudio stage. Acceptance is never inferred from demand or model approval.

## When to stop and ask

A single optimisation can run for hours, often unattended. Do not spend that time on a dead end. Stop and ask the user, with the evidence, its impact and your recommended options, as soon as one of these holds; you do not have to exhaust every tier first:

- the demand contradicts itself, or a constant, range or pass line rests on a weak basis;
- a measurement can be read in more than one way and the choice changes the result;
- the feasibility reasoning (step 1) or the first-order analysis says the structure cannot reach the objectives, or a `must` misses by a multiple of its pass line;
- the results so far give no reason to keep the current strategy (the round `brief` sets `review` when rounds stall or you are about to escalate to `global` or `structure`);
- the structure must change in a way the user has not seen.

Otherwise keep working without asking. Write a question whose answer could change the demand into `open_questions` with `blocking: true`; `round` and `opt local`, `opt hammer`, `opt global` refuse to run until it is answered. You may still run diagnostic scripts to gather evidence for the question.

## 1. Frame the need

Create the job: `uv run saos job create --name <name>`. Grill the user in rounds. Prepare a whole round before you ask anything: every question you can ask now, numbered, each with your recommended answer. Put the questions whose answer can change the structure or a pass line first and mark them, so the user can answer those even if they skip the rest. Explain optics terms in plain words. Look facts up yourself (files, `ref/docs`, the OpticStudio manual, the web) instead of asking. Then put the round to the user:

- If you have an ask-user tool (in Claude Code `AskUserQuestion`), ask through it. Your recommendation is the first option and says so; the other options are the realistic alternatives, and a value the user has to type goes into the tool's free-text answer. When the round exceeds one call's limits (Claude Code: 4 questions, 2–4 options each), ask in consecutive calls with the marked questions in the first, and do no other work between them.
- Otherwise write the round as a numbered list in which each item is a `Question:` line followed by an `Advice:` line (your recommended answer and its reason in one sentence), worded so "yes" accepts the advice.

Keep every round in `sources/interview.md`: the questions, the options or advice you showed, and the user's answers verbatim (the full text of the chosen option and anything they typed).

At the start of every session, before any other work, check the external preconditions once and ask for what is missing in your first reply: the daemon of this instance (mode, which job it holds, whether another session uses it), whether the mode you will need can start (extension mode needs a visible OpticStudio window), how many OpticStudio instances are already open against the licence, and the tools you plan to use. `uv run saos daemon status` reports the machine side in one call (`environment`: the daemon of every instance with its mode and running jobs, OpticStudio processes against the licence, visible windows, and whether extension mode can start and with which window). Do not work around a missing one silently.

**Question the structure before you write it down.** A structure the user prescribes, or asks you to change (add, remove or swap an element), is a hypothesis, not a fact: the user may not be a specialist in this part of optics, and an unreachable structure costs hours of optimisation later. Before you show the demand, reason from physics whether it can reach every `must`, and say what you find even when nobody asked:

- what each element is there to do, and whether the rest can still do it after the requested change;
- the bounds no optimiser can move: conserved or invariant quantities (étendue and the Lagrange invariant, the Petzval sum), the diffraction limit, one-way conditions such as critical angles, the space and apertures available, and how many independent degrees of freedom the structure has against how many objectives it must hold at once;
- how each part is made and what that process cannot do (coatings, surface forms, sizes, materials); find out before you make the part's shape a variable.

Work these bounds by hand, and write each estimate out so the user can follow it: the formula, its inputs with their source, the result, and what it decides. Before the user confirms, check the one or two deciding numbers on the backend with a deterministic calculation on a minimal model (a ray trace or an operand such as `RAID`, `RANG`, `REAY`, `SSAG`, `ETVA`), and say which constraints the minimal model leaves out. Do not search with an optimiser at this stage: it exploits every constraint a sketch leaves out (edge thickness, apertures, lost rays), and when it finds nothing that proves little. A verdict that only a search could decide is marginal; settle it in the first-order analysis (step 3). Before a check you expect to take more than a few minutes, tell the user how long and why. For each `must` give a verdict, reachable, marginal or not reachable, with the argument that decides it, and show it with the demand. When a verdict is marginal or not reachable, offer alternatives that change the deciding bound, not a list of variables to try.

Write `sources/demand.yaml` (copy [`demand.example.yaml`](demand.example.yaml)): the fixed `constants`, the `variables` you may adjust and their ranges, the `objectives` with their pass lines (`must`), `minimize` / `maximize` for what the user wants as small or as large as possible, and hoped-for values (`wish`), `open_questions`, and a short `summary` of the interview. Every limit (a constant's value or goal, a variable range, a pass line) names its `source`: the user, a datasheet, a paper, a textbook table, or `agent assumption: <why>`. Classifying each condition is your judgement; an unknown real-world fact is an open question, never a variable. Keep it short: no verbatim conversation, no literature details, no restated global rules. Every check must measure the real quantity; never special-case a surface type or setting to skip a measurement. A maximum or minimum over the field or the spectrum (chief ray angle, relative illumination, transmission) is measured with `ctx.cra`, `ctx.field_profile` or `ctx.wave_profile`, which sample densely, refine around the extreme and report where it is and whether the coverage was enough; when `coverage.ok` is false, sample finer or return `inf`, never the coarse value (an edge-only CRA missed 19.88° in mid field, and five wavelengths missed a transmission dip, on the nightvision job). Every check states its preconditions (parts do not intersect, the image is real, enough rays arrive, the quantity covers the whole beam and not only the surviving rays) and returns `inf` when one fails: a number from an invalid state is worse than no number. Checks are read-only: work on a copy or restore the lens, otherwise the round is refused (`LENS_MODIFIED_BY_CHECK`); writing the original values back is enough, as the last-digit rounding OpticStudio applies (relative 1e-12) is not counted as a change. When the design gives no valid value, return `inf`; raise only when the check itself cannot run. Show the demand in plain language with the feasibility verdicts, go through every limit that `uv run saos demand show --job J` lists under `weak_basis` (no outside basis) one by one, get explicit approval of its content, and record their words with `uv run saos demand confirm --job J --quote "..."`; the tools keep the full demand text the user saw. `demand confirm` also opens a small workflow window for the user (result field `ui`); reopen it with `uv run saos ui open --job J` if the user closed it or asks to see progress. It reads the job folder only and never needs your attention. Once the demand is confirmed, set the window up for this kind of system: `--tabs` picks and orders the top tabs (`layout,spot,fan,field,mtf,detectors,metrics,rounds,starts`) and `--metrics` names the demand items the Metrics tab plots per round, both remembered for the job. Choose from what the demand judges: an infinite-conjugate imaging lens usually wants `spot,fan,field,mtf` with focal length, f-number or distortion items; a microscope objective wants spot, MTF and field curvature with magnification, NA, working distance and parfocal length items; an illumination or non-sequential job wants `detectors` with its power or uniformity items. Rounds then export only the chosen spot/fan/field/MTF plots (Optiland stage), so leave out a plot only when the user does not need it; a plot not exported shows as a gap in that round. `--reset` returns to the default tabs. When the user answers by choosing an option, the quote must contain the full text of the options shown and the one chosen, not just "c".

## 3. Model, understand, describe

- Use Optiland before report acceptance. Unsupported optics are explicit capability gaps; do not start OpticStudio to fill them. Build or import through the lens commands; commands such as `lens build --as start.zmx` use a logical `.zmx` name; the backend stores `start.optiland.json` as the authoritative snapshot and `lens export` is an explicit optional ZMX export. Keep sourced materials and mechanical semi-diameters in the model. Preserve the user's window contents before any replacement after entering OpticStudio.
- For a free structure, generate starts from sourced library designs scaled to the demand. Use the most demanding field, f-number and spectral requirements to choose forms; inspect first-order and third-order predictions before investing in optimisation. There is no candidate quota. A clearly suitable form may be used directly; write why in the model notes. For a prescribed structure, show the user's reason.
- Screen every candidate without optimisation (`stages: []` in a candidates plan of `saos scan`). Then run every candidate with the same short stage budget, checks, sampling and prepare script. Generated prescriptions have no merit function: `starts.generate` requires a prepare script that sets variables and merit. The prepare keyword is required (omission is a Python TypeError); an empty value is BAD_ARGS before generation; a script that fails to compile/run or leaves merit empty returns a configuration error before screening measurements. Material failures stay distinct, and connection/UI failures propagate. For a plain candidates scan, prepare is optional only for zero optimisation or saved lenses that already have a merit function. `hypothesis` is optional. The verdict is valid, invalid within budget, or not evaluated because of material/computation failure. Equal fingerprints count once. Keep budget-limited candidates and record RuntimeWarning counts. Check scripts can suppress warnings with Python filters: zero warnings does not establish validity. Scripts can also call backend methods directly; this workflow is not a sandbox.
- Plans, input copies, the prepare copy and completed structure descriptions are sealed to detect accidental changes. The confirmation page reads existing prediction and screening records, shows their versions and matches the current model by fingerprint. Missing, stale or unmatched comparisons are warnings, never an approval or optimisation gate.
- Materials need sources in `sources/materials.yaml` (see the material-record format). The confirmation page distinguishes source found, data complete, backend supported and actually loaded; without that record, source found is unknown. A missing bound differs from a failed or absent computation.
- Write notes describing each surface, assumptions, first-order reasoning, the choice of form and `next_budget` (`max_seconds` and `plan`). Run `saos lens describe --job J --notes notes.json`, show the four sections (choice, requirements, validity, budget), then record the user's own approval with `saos lens approve`. Structural changes require a new model approval; new values, checks or comparison records alone do not. Changed checks and unmatched comparisons remain visible in the page and round response.
- Deep optimisation uses one gate: demand and model approval. Report acceptance is the gate into OpticStudio. These confirmations do not certify unknown computations. Keep `shown_sha`, unknowns and warnings with the approval. Use the workflow window for modelling; before asking the user to review, call `saos ui notify --job J --message "..."`.

Use `saos.starts.generate(ctx.job, bindings, short_seconds=..., prepare=...)` in a job script to generate the library starts; bindings map `efl_mm`, `half_field_deg`, `f_number`, `wavelengths_um` to demand item IDs. Read `library/starts/README.md` for sources, units and limits. The source examples do not establish a form’s physical limits. If strict selection finds none, `allow_extrapolation=True` explicitly permits exploratory starts outside the example field/f-number/band, retaining every exceeded condition in the plan and model page; it never changes the demand, source limits or material range checks. Different conjugates are still excluded. `saos.starts.screen(ctx, generated, workers=...)` runs all zero-optimisation candidates before the shared short stage. Generated short plans use algorithm auto; local candidate stages forward algorithm/device and retain actual selection and fallback reasons. Glass substitution uses the same local default and records distinct selections in local_algorithms. Library input and configuration failures are recorded separately from material and computation failures. Generated files live in `explore/starts/NNN/`; scans preserve their provenance and record fresh predictions. For your own prescription use `saos.starts.scale_prescription(data, K)`.

When approving a model whose structure differs under the same comparison used for rounds (appended field/wavelength samples are allowed), or whose environment declaration changes, add `--rebuild-reason` to `saos lens approve` with the reason for rebuilding. Report timing gives demand confirmation to first model approval and report acceptance; missing events remain unknown. These are recorded durations, not performance estimates. An intact earlier approval for the current structure remains usable, even if a later description is unapproved. Damaged approval records are skipped with their paths shown; if no intact approval matches, the gate refuses. Pre-seal records without approval_schema/shown and without either seal entry remain readable as legacy_unsealed; never manufacture seals for them. Report/export evidence checks still retain their own rules.

## 4. Design in rounds

Optiland local optimisation uses a step gate in both scipy and torch: each trial must be free of part interference and keep at least 95% valid rays in every configured field and wavelength on three Gaussian rings plus the chief ray. Unsafe trials are halved at most 12 times; only accepted points can become the retained best. Torch target ray bundles must additionally be valid. Automatic semi-diameters refresh after acceptance; torch history is cleared after backtracking. `opt local --help` describes `backtracks`, `step_guard_reason` and the torch acceptance counters. The torch path adds continuous squared-hinge losses for TIR, conic intersection domain, aspheric intersection residual and aperture violations through a separate guarded native trace; never treat those guarded intersections as measured optical results.

- When you resume a job, or are unsure what you are doing, reread `sources/demand.yaml` first (`uv run saos demand show --job J`).
- Use `lens set` to give surfaces what the model needs; the demand (`constants`, a variable `range`) carries the hard limits, because only the demand is judged.
- Tools: `lens surfaces/set/save/operand`, `opt vary --param radius|curvature|thickness|conic|par<N>|material [--min X --max X]`, `opt merit wizard|add|script|show`, `opt local`, `opt glass`, `opt global`, `lens analysis TYPE --set KEY=VALUE`, `scan --plan` and `exec SCRIPT` for anything ZOS-API can do (`ctx.system`, `ctx.zosapi`, `ctx.args`, `ctx.load`, `ctx.save_as`, `ctx.mark_dirty`, `ctx.path`).
- **Reach for the built-ins before you write code**; agent-written scripts cost more time than the runs they drive. In scripts, `ctx` (and the worker `w` of `ctx.map`) already has: `get`/`values`/`set` with keys `"<surface index or comment>.<radius|curvature|thickness|conic|semi_diameter|material|comment|par<N>>"`, `aperture`, `field.<n>.x|y`, `wave.<n>`, `config.<configuration>.<row>` (a value a solve overrides raises `VALUE_NOT_APPLIED`); `kept(keys)` and `restored()` to undo trials; `configuration(c)` to measure a multi-configuration lens one configuration at a time (`with ctx.configuration(c): ...` returns to the original configuration, so the checks leave the lens unchanged) and `configurations()`; `trace(rays, to)` (numpy arrays), `spot(fields, wave, grid, to, refocus)` (pass rate, chief, centroid, RMS and GEO radius per field, best focus shift), `op(name, …)`, `analysis(name, settings)`; `measure(ids)` (the demand's own checks on the current state, no evidence written: use it as the objective of any search so it means what the demand means); for non-sequential systems `nsc_trace(...)` (splitting, scattering and polarization on by default; fix `seed` in checks, which makes the result repeat exactly, and treat its `dead_ray_errors` as a precondition: rays cut off by the segment limit lower the result), `detector(object, grid)` (power, hits, pixels, irradiance map from the last trace), `ray_hits(zrd, objects, ray_filter)` (position and direction where saved rays reach given objects; a scattering medium writes about 130 kB per ray, so filter and sample), `objects()` and keys `object.<number or comment>.<param>` (position, tilt, material, `nd`/`vd`, a parameter by `par<N>` or header, `mean_path`, `vp.<DLL parameter>`, `face<N>.is|coating|fraction|sigma|rays`; `<object>@<surface>` in a mixed-mode lens); `cra`, `field_profile`, `wave_profile` (an extreme over the field or the spectrum with its location and coverage; `kit.profile` is the 1-D refinement behind them); `memo`/`lib`/`cache`. `analysis` (and `lens analysis`) returns `status` `ok`, `partial` or `empty` with `problems` and, when not `ok`, the head of OpticStudio's text export: read them to tell a model without a result from an interface limit before you rerun anything. `saos.search` has `grid`, `root` (scan then Brent, skips invalid points) and `minimize` (Nelder–Mead or Powell with budget and cancel). API, parameter keys and measured costs: `uv run saos exec --help`.
- A scan, a sweep with a per-point solve, a first-order map or a multi-start search needs no script: `uv run saos scan --job J --plan plan.json` runs it on the worker pool, measures every point with the demand's checks, ranks by shortfall and keeps the best lenses under `lenses/scans/NNN/` (plan format: `uv run saos scan --help`). Write a script only for what a plan cannot say, and then put the per-point work in a function and run it with `ctx.map("fn", items)`.
- **Keep working while it computes.** A scan you expect to run more than a few minutes goes with `--detach`: the command returns at once, the scan runs on the worker pool from a snapshot of the saved lens, and the daemon keeps serving your other commands (`lens info`, `check`, reading results, preparing the next step). Follow it with `uv run saos scan --job J --show [NNN]` (reads the files, works while the daemon is busy); `saos job cancel` stops it. A second scan or `ctx.map` while one runs gets `POOL_BUSY`; `daemon stop` waits for you to cancel or finish it (`BUSY`). Any `exec`, `opt local|hammer|global`, `check` or `round` that may outlast your own command time limit goes with `--detach`: it returns `runs/NNN-<op>.json` at once, a detached process waits for the daemon and writes the full response there (`status` `running`, `done` or `failed`), and `uv run saos job show J` lists the recent runs next to the progress. While the daemon runs a long operation every other request fails at once with `BUSY` (details name the running operation) instead of queueing; wait or `saos job cancel`, never resend it. A 250.6 s computation once looked failed to a 240 s client and was nearly submitted again.
- **Changing the checks is safe.** Check code includes `checks/` and the saos recipe libraries and `saos.kit` it uses. When it changes, the next `saos round` first re-measures the best round so far with the new checks (a ledger row with tier `rebase` pointing at the old archived lens) and compares from there. If the numbers are the same (a speed-up, a switch to kit or a recipe), the comparison window goes on; if they differ, a new window starts at that row, and the old best lens stays deliverable under the new checks. The round result shows it under `rebase` (`equivalent`, `diffs`); an unintended difference is a bug in the new checks, an intended one is a demand question. A new window does not reset `max_rounds`, and after `limit` or `stopped` changed checks are refused like any other round.
- Use the saos optimisers and Zemax merit operands. In an Optiland session `saos opt local` runs in process without a licence: `--algorithm auto` (default) prefers `torch-trf` on CPU float64 and falls back to `trf` only for an identified differentiability gap. Explicit algorithm choices never fall back. Explicit alternatives are `trf` (keeps `opt vary --min/--max` bounds), `lm` and `lbfgsb` with numerical derivatives, derivative-free `nelder-mead` and `powell`, or `torch-trf` / `torch-lbfgs` / `torch-adam` by autograd when the merit holds only RSCE, RWCE, REAY, EFFL, TOTR, CTVA, ETVA and their boundary rows (auto falls back for unsupported operands, variables/solves or a scalar script loss without a gradient connection; explicitly requested torch reports the gap. A loss script for torch returns a scalar Tensor connected to the variables via `ctx.backend.torch_operand(...)`); `opt merit script loss.py` adds `def loss(ctx)` as one more merit row (a non-negative residual the optimiser drives to 0, e.g. a demand check via `ctx.measure`). Results record `requested_algorithm`, the actual `algorithm`, and `fallback` (null or from/to/reason/message). Script bugs, numerical failures, cancellation and timeout never trigger an automatic retry. Fallback consumes the remaining budget. The computation budget starts before the initial measurements and includes final measurements, review and search archiving; Optiland Python loops have internal interruption checkpoints, while native C/CUDA calls and atomic file writes must return first. On expiry the optimiser restores a verified snapshot without retracing. An unfinished review returns `completed: false, valid: false`: finish the demand/interference checks before recording a round. `improved` and `converged` are separate; Optiland `succeeded` requires both, an admissible saved point and no interruption. `stopped_by` is null, timeout or cancel. Missing measurements are null, never Infinity. `torch-trf` uses Torch residuals/Jacobians with a SciPy trust-region solver; it does not use finite-difference Jacobians. Real-ray autograd currently requires centered, unfolded systems with angle/object-height fields; other aiming geometries report a capability gap. The result says whether the loop edited the live lens (`inner_loop` `live` for SciPy, `torch` for autograd) or rebuilt it each step (`rebuild`, slower: a variable or solve it cannot set in place). In Optiland `saos opt global --max-seconds S [--method de|basinhopping|shgo]` searches with scipy (de and shgo need `--min/--max` on every variable) and keeps its ten best systems free of interference, and `saos opt glass [--surfaces R] [--catalog C]` substitutes glasses of an in-production catalog (default `SAOS_CDGM_INPROD`) by a greedy neighbour search that re-optimises every candidate; `opt vary --param material --mode model` lets nd/Vd vary as an Optiland approximation of a model glass, which rounds and the report label and which must become a real glass before the OpticStudio stage. `saos opt hammer --max-seconds S` runs in OpticStudio. Hammer and global search never end on their own; the budget is required, they cancel at it and leave the best system in the editor, and global search moves its ten best to `lenses/global/NNN/`. To search again from one of them, `lens save --as` it elsewhere first; global search refuses to run next to existing `GLOPT_*` lenses (`.zmx` or `.optiland.json`), which it would overwrite. In OpticStudio, glass substitution (`opt vary --param material --mode substitute`) only happens in Hammer or global search, within one catalog per surface. Without `--catalog` it uses `SAOS_CDGM_INPROD` (glasses CDGM lists as Standard or Preferred; `SAOS_NHG_INPROD` is the same for New Huaguang), and the result names the catalog. `outside_catalog` lists surfaces whose current glass is not in it: substitution will move them to that catalog's glasses, so pass `--catalog` per surface where the maker must stay. A maker's full catalog often yields discontinued glasses (9 of 12 substitutions on the Cooke sample in SCHOTT were Obsolete), so read `materials_changed` in the result: an `Obsolete` glass is usually unavailable; replace it with a glass in production or ask the user before you deliver it. In every case make sure the merit function measures what the demand means and cannot be satisfied by a loophole (for example by discarding light or leaving the physical part). Every optimiser result carries `review`: the interference check after the run (crossings, overlaps, thinnest glass, smallest air gap) and, with `--measure <ids>|hard|all`, the demand's checks before and after with the items that got `better` or `worse`; `valid` is false when parts intersect or a hard limit fails. Pass `--measure` with the fast checks the merit function stands in for, and treat a run that lowered the merit but made `worse` non-empty or `valid` false as no progress. When an optimiser fails mid-run the lens is marked unsaved: the editor holds what it reached (`lens save --as` keeps it, `lens load --discard` drops it).
- Optimise on smooth proxies (RMS spot or wavefront operands, Seidel terms, real-ray constraints); use the demand checks to judge. Step-like checks (ray counts, a field scanned in steps) give an optimiser almost no gradient. Slow checks cost every evaluation of a search: read each item's `duration_s` from a `saos check` first, and when a search must use the demand's own measurement (`ctx.measure(ids)`, a scan's `measure`, a `minimize` plan) give it only the items its variables act on and that take well under a second; leave the slow ones (a Huygens PSF series takes several seconds) to `saos check --only` and the round. A Nelder–Mead on the full shortfall of the fibre probe (18 variables, one-hour budget) stopped unconverged after 48 evaluations (2026-10-18).
- An optimiser exploits whatever the target leaves open. Physically impossible states (intersecting parts, a virtual focus, rays missing the image, light leaving the part) must make the target invalid, not cost a linear penalty. A merit value OpticStudio cannot compute (for example 9e+09 when rays fail by total internal reflection) is a diagnosis signal: find the cause before going on, never skip it as noise.
- When you optimise outside the lens's merit function (your own `exec` loop), record the value you actually optimised with `saos round --merit <value>`; otherwise the ledger shows whatever merit function the lens file holds.
- Weigh the merit function the way the demand weighs the objectives: one structure rarely meets everything, and the compromise should favour the user's objectives.
- Record a round when you have a design worth judging against the demand: after an optimisation run, a material substitution or a structural change, not after every tweak. Each round should link the lens hash, the strategy (`--tier`), the budget and constraint changes (`--note`) and the evaluation; a long run history with an empty ledger leaves the stop rule nothing to judge (one round after 59 scripts on the nightvision job). Once the design phase has seen two optimisations or fifteen scripts since the last round, `opt`, `exec` and `scan` results carry `since_round` with a reminder. Small trial changes go through `saos check` (measures without recording) or `explore/`; `saos check --only <id>,<id>` measures just the items your change can affect (the result is `partial` and never achieved; every round measures all items). Each measured item reports `duration_s`, so you can see which checks are slow. `uv run saos round --job J --tier <tier>[,<tier>…] --note "<what you did>"`; name every tier the round used. Tiers, low to high: `local`, `variables`, `materials` (substitute sourced materials: `opt glass` in the Optiland stage, Hammer or global search with `--mode substitute` in OpticStudio), `global`, `structure`. The ladder is a record of what was tried, not an order to follow: when your evidence says a tier cannot help, rule it out with `uv run saos rule-out --job J --tier <tier> --reason "<evidence, e.g. scans/NNN>"` instead of spending a round on it (it holds until the next clear gain). Read the decision (`achieved`, `exhausted`, `limit`, `continue` with `next_tier`); compare rounds by the shortfall, never by the merit value. Every round also runs the interference check out to the parts' outer edges: a round whose parts cross or interpenetrate carries `parts_clash`, is never achieved and cannot be delivered, whatever its checks say. Each round also exports `evaluations/NNN/viz.json` (layout, spot, ray fan, field curvature/distortion and MTF data) for the user's window; a failed export is reported under `viz` and does not affect the round.
- If the structure must change in a way the approved description does not cover, describe the new model and get it approved before recording rounds on it.
- **Gate expensive runs on the gap.** Before a run you expect to take more than about ten minutes, or any `global` or `structure` attempt, tell the user for each failing `must` how far it is off, the mechanism you expect to close it, the variables that act on that mechanism and a rough expected gain. When an objective misses by a multiple of its pass line rather than a fraction, or a diagnosis already shows a cap in this structure (light clipped by an aperture the variables cannot widen, an aberration the variables cannot change), optimising is not the next step: diagnose (below) and take the result to the user.
- **Accuracy follows reachability.** Convergence and sampling audits (finer ray grids, more segments, more directions) earn their time once the design is close to its pass lines. While it misses by a multiple, sample just finely enough that the verdict cannot flip.

### Diagnose before you escalate

When progress stalls, before an expensive escalation, or when a round `brief` sets `review`, think from geometrical optics instead of trying everything. How much of the following you need depends on the system and on what you already know; skip what the evidence already settles.

Is the target reachable at all? A useful ladder, from the cheapest test: conserved quantities and invariants (étendue, the Lagrange invariant, the Petzval sum); one point on axis under every real constraint (apertures, clearances, pass rate, TIR); the full field. A failure low on the ladder is a structure question, and optimising higher up is wasted.

Which variables move the target?

1. Name the objective with the largest weighted gap and the mechanism behind it: which aberration or limit (spherical, coma, astigmatism, field curvature, distortion, axial or lateral colour, vignetting, aperture, Lagrange invariant), seen in Seidel terms, ray fans, field curves or pass rates.
2. Reason which parts of the structure can change that mechanism and which cannot. Some quantities are invariant to whole classes of variables: the Petzval sum depends only on surface powers and indices, so aspheric and freeform terms only trade field curvature for astigmatism. Probe the few variables your reasoning ranks highest (a plan takes 1–6). A control that should not move the target is worth adding whenever the ranking decides what you optimise: without it a small effect cannot be told from noise.
3. Write the predictions first (mechanism, direction, rough size), then save the lens and run the probes as a scan: `uv run saos scan --job J --plan plan.json` with a `probes` plan. The base and every probe at ±delta (2N+1 points) run at once on the worker pool, each from the saved lens, with a compensator (`"compensate": "quick_focus"`, your own script `run(w)`, or a `solve`) so that defocus does not hide the aberration (Quick Focus moves the thickness before the image surface and can fail silently on folded or partly failing systems; the result says so when it never moved); choose delta as a meaningful fraction of the variable's allowed range. The lens is left unchanged; everything goes to `scans/NNN/`.
4. Read `ranking` and `review`. An observed `valley` (or `peak`) means both sides moved the target the same way: the variable is already at its optimum there, which says nothing about the structure. Optimise first on the variables that move the target. If a prediction failed or a control moved, your model of the system is wrong: fix that before optimising. If nothing moves the target and your first-order reasoning agrees, it is a structure question: rule out the tiers that cannot help (`saos rule-out`, citing `scans/NNN`) and go to `structure`, or ask the user.

Plan format:

```json
{"target": "spot", "mechanism": "Petzval field curvature: ~73 um sag at 150 um image height",
 "compensate": "quick_focus",
 "probes": [
   {"id": "l1_rear_r", "key": "3.radius", "delta": 0.02,
    "prediction": "less lens-1 power lowers the Petzval sum; spot down by a few um", "expect": {"spot": "down"}},
   {"id": "l2_a4", "script": "explore/l2_a4.py", "delta": 0.001, "control": true,
    "prediction": "trades astigmatism only, Petzval unchanged", "expect": {"spot": "none"}}]}
```

A built-in change is a parameter `key` as in scripts (`"3.radius"`, `"lens dome.conic"`, `"12.par1"`; a flat surface is probed by its `curvature`); anything else is a script under the job defining `run(w, delta)`. `measure` (optional) lists the demand items to measure; the default is every item with a bound.

## 5. Deliver

When the demand or the user cares how the design survives manufacturing and assembly, run a tolerance scan on the lens of the round you will deliver before the report: load that round's lens, then `saos scan --job J --plan plan.json` with `{"tolerance": {"items": [{"key", "min", "max", "dist"?, "relative"?, "source"}], "samples": N, "seed": S, "sensitivity": true}, "compensate": …}`. Every item names a numeric parameter as in scripts (thicknesses, radii or curvatures, `<surface>.nd` / `.vd` for index and Abbe errors, `object.<n>.x|tilt_x|…` for non-sequential parts, coordinate-break `par<N>` for element tilts and decenters) with deviations from nominal and a `source` (a maker's table, the user's words, a standard): never invent tolerances, ask for them as for any other bound. The scan measures the demand's own checks: sensitivity (each item alone at its limits) ranks what matters, Monte Carlo gives each check's distribution and pass rate and the yield (all hard bounds met, all measured goals met). Choose the sample count from the yield precision the user needs (the standard error of a yield p from N samples is about √(p(1−p)/N)); non-sequential checks trace per sample, so estimate the time from one check run first. The report includes the latest tolerance scan and says whether it ran on the delivered lens. Without such a need, skip it and offer it when you hand over the report.

`uv run saos report --job J` writes `report/index.html` in the user's language: status, the delivered lens (the achieved round with the smallest shortfall, else the smallest shortfall among deliverable rounds), its materials, and for each unmet goal how far it is off. With no valid round it says so instead of naming a "best" lens. Its JSON result names a lens in `deliver` only when that lens is deliverable (`deliverable`, `headline`); otherwise `deliver` is null and the round shown for diagnosis is under `diagnostic`, so never pass it on as the delivery. Give the user the path; if no tolerance scan was run, say that one can follow. When the result's `backend` is `optiland` (`opticstudio_verified` false), the page says the numbers are Optiland's and not yet verified in OpticStudio; tell the user so. Verifying in OpticStudio and optimising further there, with a new round limit, comes only after the user accepts this result; run `uv run saos zos begin --job J --quote "<their words>" [--round N] [--max-rounds K]` after that acceptance. The selected round must be deliverable under the current demand and checks and contain no Optiland model-glass approximations. Regenerate an outdated report before asking for acceptance. The entry rebuilds from the archived prescription, never from the Optiland-written `.zmx`, records a `verify` round with the same checks and writes item, baseline and material comparisons. Differences have no pass threshold; use OpticStudio numbers. An unavailable licence leaves the entry unrecorded: explain the failure and retry when available. Resume an interrupted entry with the same arguments; a committed verify round is not duplicated. If the user rejects the report, continue designing in Optiland within the current demand and stop rules, or record their decision with `saos stop`; do not enter OpticStudio.

After entry, the job stays in OpticStudio across lens loads, builds and daemon restarts. Continue with `opt local` (DLS), `opt hammer`, `opt global`, worker scans and `saos round`; the comparison window and round budget restart at the verify baseline, with `--max-rounds` or the demand limit. The five design tiers and stop rules remain the same. Recreate each optimisation setting listed in `untranslated`; variable bounds and merit scripts do not silently become Zemax constraints. Reports select only this stage's rounds and retain the accepted Optiland conclusion and comparisons.

Stopping is a conclusion too. When the evidence says the demand cannot be met with what is allowed, show the user the evidence and the options; when they decide to stop, record it with `uv run saos stop --job J --reason "<why, citing the evidence>" --quote "<their words, with the option text>"`. Only the user's decision stops the rounds; the report then shows the reason and their words.

## Compute

- Every optical number is computed by the backend (Optiland or OpticStudio), first-order numbers included (paraxial operands such as `EFFL`, `PMAG`, `PARY`, `PARA`, Seidel terms, ray traces, analyses). Do not write your own ray tracer, aberration or paraxial calculator, surrogate model or GPU code (ADR-0012). Python scripts may hold the control logic, such as scans, multi-starts, sequencing and bookkeeping, as long as every evaluation goes through `ctx` (or the ZOS-API under `SAOS_BACKEND=zos`). This rule is about code and about the numbers you decide on: reasoning with hand estimates to question a structure or choose a direction is expected (step 1), and the estimate that decides is then checked in OpticStudio.
- Optiland workers are the default during exploration and use no licences; the default count is the available CPU count minus two (at least one). After `zos begin`, workers use standalone OpticStudio and default to four. Pools retain warm workers and replace them when the backend changes. The following timing measurements describe the older OpticStudio pool only. Normally one OpticStudio instance does the work in that stage. When many independent evaluations are needed (a scan, multi-starts, a sensitivity table), run them concurrently: `saos scan`, or `ctx.map("<function of this script>", items, workers=N)` in a `saos exec` script (`"explore/x.py:fn"` for a function in another job file). The function runs as `fn(w, item)` in a worker, its own standalone instance, which reloads a copy of the saved lens before every item. The workers stay up in the daemon between calls and close after 10 idle minutes (`ctx.pool_close()` frees the licences at once), so only the first call pays the start-up of 5.8–7.9 s per instance (measured 2026-10-17). Measured on this machine: with the pool up, 36 points of a solve-and-measure scan took 6.76, 3.83, 2.21 and 1.63 s on 1, 2, 4 and 6 workers; started cold, the same 4-worker scan took 10.2 s against 5.25 s serial in the daemon, so start a pool only for work that outlasts the start-up or will be repeated. The licence allows 8 OpticStudio instances at a time, the user's open windows and this daemon included; count them (`daemon status`) before choosing `workers`, and expect a refused worker to be reported as unavailable. Results and the script copy go to `parallel/NNN/` (`scans/NNN/` for `saos scan`).
- Per-point work that searches (find the curvature that puts the focus at the working distance, a best-focus solve) uses `search.root` rather than a coarse scan plus bisection: in the measured example it took 58% fewer evaluations for the same answer.
- Every number you base a decision on uses one definition: optimisation targets, your scripts' evaluations, first-order estimates and the merit value in the ledger use the same sampling, constraints and definition as the demand checks, or have been compared with the checks on the same lens before you draw a conclusion. A reduced or simplified OpticStudio model (paraxial surfaces, a coarse ray grid, one field) states which constraints it drops, and its key prediction is tested on the real lens before you act on it.
- Times and numbers in notes and messages come from tool output (results, logs, `saos job show`), never from memory or estimate; label an estimate as one.
- Leave 2 logical cores to the user and use the rest (`saos opt local`, `hammer` and `global` do this by default); start your own long-running processes at below-normal priority so the user's work stays responsive.
- Long runs are visible and stoppable. `opt local`, `opt hammer`, `opt global`, `opt glass`, `zos begin`, `round`, `check`, `scan` and `exec` write the job's `progress.json` (a detached scan writes `scans/NNN/progress.json`); `uv run saos job show <job>` reads it while the daemon is busy. Give `opt local` a `--max-seconds` budget; `opt hammer` and `opt global` require one. In a long script call `ctx.progress(stage, **numbers)` at checkpoints; it returns True after `uv run saos job cancel <job>`, and the script then stops at a safe point and keeps what it has (`ctx.cancel_requested()` checks without reporting). A client timeout only stops waiting; the daemon keeps computing until it finishes or is cancelled, and the error says so (`still_running`). A failure to write `progress.json` (the workflow window reading it can make Windows refuse the replace) is retried and then only logged; it never stops the computation. Tell the user what is running, where and how to follow it, and the numbers at each checkpoint; stop a run when a checkpoint interval gains less than the demand's `rel` instead of holding the instance.

## Context economy

Read a large file by section (find the headings, read the part you need), and read a helper library only when you are about to use or change it. Material and bought-in part searches that should end in one table (part numbers, sizes, indices, dispersion data) go to the `optic-material-explorer` agent when it is available (`~/.claude/agents/`): give it the hard limits, the columns you need and a download folder under the job's `sources/`; it returns a sourced candidate table, an exclusion table and the files it saved. Without it, search yourself as the Materials bullet in step 3 says. Before a long piece of work, ask whether its result can still change what you do next; if a pending question could make it obsolete, wait for the answer.

## Explicit debugging (on-screen)

The workflow window is how the user watches (step 3). Extension mode is optional on top of it: when the user also wants the OpticStudio window, start with `uv run saos daemon start --mode extension` (set `SAOS_UI_PID` if several OpticStudio windows are open). saos opens Lens Data and a layout window: the cross-section, or the 3D viewer when OpticStudio cannot draw a cross-section (non-axial or non-sequential systems; the result's `layout.fallback_reason` says why). Add an analysis worth watching with `lens view --analysis TYPE`; `--viewer cross-section|3d|shaded` picks another layout. Windows refresh after every lens-changing command. `lens screenshot` captures PNGs. On `UI_BLOCKED`, ask the user to close the named dialog. Before `lens load`, `unload` or `build` replace the window content, saos saves unsaved window content to `lenses/captures/NNN-unsaved.zmx` (returned as `captured`); tell the user where their work went. `ctx.load` in scripts does the same; call `ctx.capture_window()` first in a script that replaces the window content. Your own unsaved changes are refused until you `lens save` or pass `--discard`, which drops only your changes. Long operations (exec, check, round, scan, opt) pause window updates while they run and refresh once at the end, because live updates once made an evaluation 4.5 times slower; `exec --live` or `SAOS_UI_LIVE=1` keeps the windows live when the user wants to watch the steps.
