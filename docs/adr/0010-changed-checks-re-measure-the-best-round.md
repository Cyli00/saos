# 判定代码改动后先重测最好的一轮

用户决定（2026-10-17）：判定代码一改就重开比较窗口，会让没人愿意给检查提速；光纤任务的检查库每次判定都把同一批追迹重算好几遍，改写它却会让“最后一次明显进步”从头算起，旧窗口里最好的镜头也不能交付。

判定版本（`checks/` 全部文件，加上它们引用的 saos 配方包和 `saos.kit` 源码）在同一需求下变了时，`saos round` 先用新判定重测当前窗口目标差距最小的一轮的归档镜头，写成 ledger 中 tier 为 `rebase` 的一条（`file` 仍指向原归档镜头，`rebase_of` 指向原轮次），再记录本轮。各项数值在相对 1e-9 内与原记录一致、没有判定出错，这条记为 `equivalent`，比较窗口延续；否则从这条开始新窗口。重测记录不计入轮次上限和“没有进步的轮数”，满足交付条件时可以交付。

## Considered Options

- 维持原规则，判定代码一改就重开窗口：最简单，但惩罚提速，旧的最好镜头也失去可交付身份。
- 单独的 `saos reverify` 命令，在最近几轮上重测并把新旧版本写进 `method_links.jsonl`（同日实现后撤回）：要 agent 记得先跑，窗口靠链接表推算，多了一个命令、一个文件和一套版本映射；数值不同时旧的最好镜头仍不能交付。
- 每次判定改动都重测窗口内所有轮次：轮次多时太慢。只重测最好的一轮已经给出新窗口的起点，多花一次判定的时间（光纤任务一次判定约 9–12 s）。

## Consequences

判定版本只看重测的那一轮：如果新判定只在别的镜头上给出不同数值，这里发现不了，之后的轮次会用新数值比较。等价只在同一个需求版本内成立；需求一变，窗口照旧重开，不做重测。旧记录没有判定版本时，重测结果不触发“已终止”的拒绝。
