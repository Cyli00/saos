# 后台进程在回复之后自动刷新当前镜头视图和指标

2026-10-30，用户要求流程图窗口的信息及时、充分，各种指标齐全，并且由后台全自动更新，不靠模型主动调用命令。原来的做法有三处缺口：`view.json` 只在 8 个操作（lens load/set/build、opt local/hammer/global、exec、round）之后重写，`opt vary`、`opt merit`、`lens save`、后端切换之后窗口不变；当前镜头只有几何，评价函数值和需求各项只在记过的轮次上看得到，`saos check` 的结果从不显示；“指标”页要 agent 先用 `ui open --metrics` 选条目，记轮次时只导出 `--tabs` 选中的图（OpticStudio 后端其实忽略这个限制，只有 rtc 照做）。用户选了三项：当前镜头实时指标、按镜头变化自动刷新、指标与绘图默认全开。

## 做法

- **反过来列不刷新的操作**：`VIEW_KEEPS` 列出不改镜头的操作（只读、保存、判定、扫描等）；其余操作，包括以后新加的，不论成败都刷新；切换了后端的操作也刷新。`lens save` 只改写 `view.json` 里的文件名和未保存标记。
- **回复之后再做**：刷新放在 `serve` 循环发出回复、读下一个请求之前（`Daemon.idle`），agent 拿到结果不再等导出。实测 OpticStudio 上导出一次当前视图要 1.3–4.5 s（`work/` 下 7 个任务的 `view.json` 计时，几何 1.4–1.6 s、`describe_model` 2.6–2.9 s）；rtc 上 `tests/fixtures/cases/sequential.zmx` 一次刷新（视图加两项操作数指标）24–34 ms，其中视图 11 ms（2026-10-30 本机）。下一个请求仍排在刷新之后，所以阶段判断和后端路由读到的 `view.json` 总是新的。
- **当前镜头指标**：刷新后测评价函数值和需求里每一个带判定方法的条目（`saos.live`，用 `demand.quick` 的同一套定义，不存证据），写进任务的 `metrics.json`。每次限时 `SAOS_LIVE_S`（默认 3 s，0 关闭）：限时用完时没测到的项下次排在最前；单项就超过限时的项不再自动测，取 `saos check` 和 `saos round` 的值。`saos check` 与 `saos round` 刚测过的值直接写入，不重测。每个值记下测它时的视图版本（进程号加序号），界面把镜头改动之前的值标灰。
- **判定脚本改了镜头**：自动测量前后比较各面数据，改了就把镜头标为未保存，并暂停自动测量直到判定代码改过（与 `saos check` 的 `lens_modified_by_checks` 同一个问题）。
- **长脚本**：`ctx.progress()` 顺带刷新当前视图，间隔取 5 s 与导出耗时的 10 倍中较大的一个，导出至多占运行时间的约 10%；`ctx.show()` 仍可立即推送。
- **默认全开**：没选条目时“指标”页显示所有带判定方法的条目，选了只改顺序和范围；轮次总是导出全部分析图，`viz_data` 去掉 `plots` 参数。窗口顶栏显示当前镜头的评价函数值和 G。

## 代价与限制

- 连着发命令时，后一个命令要等前一个的刷新：OpticStudio 上视图最多约 4.5 s，加指标限时 3 s；agent 两条命令之间通常要思考几秒，大多看不到这段等待。没在多轮任务上实测。
- 自动测量运行用户的判定脚本。在 OpticStudio 上，单项第一次测量就可能超过限时（例如 Huygens PSF），这一次的耗时照样发生，之后不再自动测。
- 运行中（`progress.json` 为 running）窗口把指标都标为“镜头改动之前”，因为运行中视图会更新而指标不会。

## 2026-11-03 后续实现范围

[ADR-0022](0022-metric-catalog-and-live-metrics.md) 修订 rtc 路径：目录指标由独立进程加载完整镜头快照，优化回调和空闲刷新均可提交，不在主循环运行任意判定脚本。旧的非目录判定保留最近一次正式测量值。OpticStudio 继续使用本文的原有测量预算与刷新方式。

因此，“运行中指标都属于镜头改动之前”只描述旧实现及当前 OpticStudio 路径；rtc 的目录项应按各项视图版本判断。前述历史计时不代表新实时进程性能；用户要求本轮不执行任何测试与验证。
